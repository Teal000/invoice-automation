# Evaluation methodology

How the numbers in `evaluation/results/` were produced, what they mean, and
what they do not. One rule governs this file: a figure here is either
reproducible from a documented command or it does not belong here.

## Reproducing it

```powershell
.\.venv\Scripts\python.exe data\generate_corpus.py
```

```powershell
.\.venv\Scripts\python.exe evaluation\run_benchmark.py --split development
```

Then `--split validation`, and `--split test` once. Each writes a JSON file
with every case and a Markdown summary into `evaluation/results/`.

Generation is deterministic from a single seed, so a regenerated corpus is
byte-identical to the committed one. Both the documents and the manifest are
committed, which is what makes "the frozen test set" mean something: it is a
specific set of bytes in git history, not a description of one.

## The corpus

200 synthetic documents, generated by `data/generate_corpus.py` from seeded
payloads. Each payload **is** the ground truth — no hand labelling, so the
labels cannot drift from the documents.

| Split | Documents | Layouts |
|---|---|---|
| development | 120 | atlas, medina, carthage |
| validation | 40 | the above plus sousse |
| test (frozen) | 40 | the above plus **kairouan**, which the extractor is never taught |

76 documents are clean, 100 carry a fault a rule is designed to catch, and 24
carry a fault **no rule can catch**. The suppliers (12) and purchase orders
are generated with the corpus and live in `data/corpus/reference/`.

Three decisions shape what the numbers are worth.

**Two layouts the extractor did not start with.** `sousse` was taught during
this work, which is what the validation split exists to check. `kairouan`
appears only in the frozen test split and is never taught. A benchmark where
every layout is familiar measures the extractor against its own assumptions
and reports a number that cannot fall.

**Faults nothing can detect, on purpose.** If every seeded fault maps to a
rule, "recall" restates the rule table. So the corpus also seeds: a supplier
name that disagrees with a correct supplier code, an invoice dated next year,
a line billed with quantity zero, and the same line entered twice. Each is
arithmetically consistent and each is labelled `detectable: false`.

**Duplicate families stay in one split.** An exact resend and a near-duplicate
of the same invoice are generated together and assigned together, so no split
is scored on a document whose twin sat in another.

## What is measured, and separately

**Extraction** — did the extractor recover the values the document was drawn
from? Both sides go through the same normalisation, so a date is compared as
a date and an amount as a `Decimal`: the question is whether the meaning
survived, not the formatting. Reported for familiar layouts and the unseen
layout separately, because averaging them hides the only figure that
generalises.

**Pipeline conformance** — did each document reach the state and the exception
codes it is labelled with? This is a specification test. It says the
implementation matches its own rules; it is not evidence that the rules are
the right ones.

**Fault detection** — of the faults actually seeded, how many did the rules
flag? Reported over *all* seeded faults, over the detectable ones, and over
the undetectable ones. A document whose layout cannot be read fails
`REQUIRED_FIELD_MISSING` whatever is wrong with it, so flags of that kind on
an unreadable document are counted separately and must not be read as
detection.

## Results

Run on 6 November 2026. Full figures in `evaluation/results/`.

| | development (120) | validation (40) | **test, frozen (40)** |
|---|---|---|---|
| Layout identified, familiar | 120/120 | 40/40 | 32/32 |
| Layout identified, **unseen** | — | — | **0/8** |
| Critical fields, familiar | 120/120 | 40/40 | 32/32 |
| Critical fields, **unseen** | — | — | **0/8** |
| Values invented on the unseen layout | — | — | **0** |
| Pipeline conformance | 120/120 | 40/40 | 32/40 |
| Fault recall, all seeded | 60/78 | 21/22 | 20/24 |
| Fault recall, detectable | 60/60 | 21/21 | 19/19 |
| Fault recall, **undetectable** | **0/18** | **0/1** | **1/5** |

### Reading them

On layouts it was taught, the extractor recovers every critical field and the
pipeline reaches the labelled outcome every time. That is a correctness
result on synthetic documents, not a performance claim about real invoices.

On the layout it was never taught, it identifies nothing, recovers nothing,
and **invents nothing**. Those eight documents fail
`REQUIRED_FIELD_MISSING` and go to review. That is the designed failure, and
it is the reason conformance on the test split is 32/40 rather than 40/40:
the eight unreadable documents do not reach the state their labels describe.
Reporting 32/40 instead of quietly excluding them is the point.

The rules catch every fault they were built for and **none** of the faults
they were not. The single undetectable fault that was flagged in the test
split (`tes_0009`) was flagged only because its layout was unreadable, so
every field was reported missing — not because the future-dated invoice was
noticed. The benchmark counts that case separately for exactly this reason.

## What these numbers do not establish

- **Synthetic documents from one generator.** Real supplier invoices vary in
  ways a generator does not anticipate. The unseen-layout column is the
  closest thing here to evidence about an unfamiliar document, and it says
  the extractor reads nothing.
- **Digitally generated PDFs with a text layer.** No scans, no OCR.
- **Nothing about effort or time.** No timing has been done, so no claim
  about saved effort appears anywhere in this repository.
- **One machine, one run.** No variance, no confidence intervals. With 40
  documents in the test split, an interval would be wide enough to be
  useless and quoting one would dress up a small sample as a measurement.

## What has not been measured

- Human handling time, with or without the workflow.
- Processing latency and cost per document.
- Recovery success as a rate. One recovery path is covered by an integration
  test that injects a failure; it is not a measured rate over trials.
- Anything about scanned documents.

## What would improve this next

1. **Real documents**, with permission and anonymised, reported separately.
   This is the only thing that can speak to readiness, and it would most
   likely show the extractor failing often — which is the point of measuring.
2. **More fault types the rules do not target**, to keep the blind-spot
   figure honest as rules are added.
3. **A timed manual comparison** on 20–30 cases of similar difficulty, with
   who did the work and in what order recorded. Until that exists, no claim
   about effort saved can be made at all.
