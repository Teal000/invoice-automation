# n8n workflows

Three workflows, generated by `build_workflows.py` so the node type versions
live in one place. They import into n8n and **they do not yet run**. What that
means precisely is below; nothing here should be read as working.

## State, as of 5 November 2026

| Step | State |
|---|---|
| Node type versions read from the running n8n (not guessed) | Done |
| Generated and committed, with no secret in them | Done |
| Imported into n8n 2.46.6 (`n8n import:workflow`) | Done — 3 workflows |
| Credential seeded inside the container from its own environment | Done |
| Published so the triggers register | **Not working** |
| Executed end to end | **Not done** |

The webhook accepts a POST and returns 200, but the workflow stops at the
webhook node: the submission it names stays `pending`, and the API logs show
no call arriving from n8n. n8n's own log says
`Processed 0 draft workflows, 0 published workflows` after every restart.

Two things were learned on the way and are already fixed in the generator:

* The first version read the API base URL and key from `$env` in expressions.
  n8n blocks that by default — the execution failed with
  `access to env vars denied`. Rather than disable n8n's expression sandbox
  for every workflow, the key now lives in a credential and the base URL is
  written in the workflow.
* `n8n update:workflow --active=true` is **deprecated** in 2.x in favour of
  `publish:workflow` / `unpublish:workflow`. n8n 2.x separates draft from
  published versions, and the old flag does not publish.

`publish:workflow` was then used, and the count still reads zero published.
That is where it stands.

## What is needed next

The editor would show the actual state of each workflow — whether it is a
draft, whether the trigger registered, and what the last execution did — and
would publish them in one click. It needs an owner account to be created at
http://localhost:5678, which is the account holder's to create, not something
to automate.

After that: open each workflow, publish it, then fire the webhook with a real
submission id and confirm the invoice reaches an outcome.

## What the workflows do

**Process a submission** (webhook). Receives `{"submission_id": "..."}`, calls
`POST /submissions/{id}/process`, and routes on the result: review needed, no
action, or a failure that outlasted the retries. The HTTP node retries three
times with a five-second wait and continues on its error output, so a failure
is visible rather than silent.

It deliberately does **not** check first whether the submission was already
processed. The API refuses to process a settled submission and reports what
was recorded, so re-implementing that check here would create a second
opinion about the same question — and the orchestrator would be the one that
is wrong after a race.

**Recover stalled work** (every fifteen minutes). Calls `POST /jobs/recover`
and separates "something still needs a person" from "nothing outstanding".

**Read pending notifications** (every five minutes). Reads
`GET /notifications?status=pending` and stops there. Nothing in this project
delivers a notification, and a workflow that marked them sent without sending
them would put a falsehood in the database. When a mail or chat node is
added, the next step becomes `POST /notifications/{id}/sent` naming that
channel.

## Regenerating

```powershell
.\.venv\Scripts\python.exe workflows\n8n\build_workflows.py
```

Then, from the project root with the stack up:

```bash
docker compose exec n8n n8n import:workflow --separate --input=/workflows
```

On Windows in Git Bash, prefix that with `MSYS_NO_PATHCONV=1` or the POSIX
path is rewritten to a Windows one and the import silently finds nothing.

The exports carry no secret. The credential is seeded separately, inside the
container, from the environment compose already gives it.
