## What was learned getting this far

Each of these cost a round trip and is worth not rediscovering.

**An owner account is required before publishing does anything.** Before one
existed, `publish:workflow` reported success and n8n logged
`0 published workflows` after every restart. With an account, the same command
produced `3 published workflows`. CLI-imported workflows appear to need an
owning project, which cannot exist without a user.

**`update:workflow --active=true` is deprecated and actively harmful here.**
n8n 2.x replaces it with `publish:workflow` / `unpublish:workflow`, and 2.x
separates a draft version from a published one. Running the deprecated command
on published workflows moved them back to `0 published`.

**n8n blocks `$env` in expressions by default.** The first version read the API
base URL and key that way and failed at run time with
`access to env vars denied`. Disabling that block would weaken n8n's sandbox
for every workflow, so the key now lives in a credential and the base URL is
written into the workflow.

**Import without a fixed `id` creates a copy every time.** Three imports left
nine workflows. Two of them registered the same webhook path, which n8n
reported as
`UNIQUE constraint failed: webhook_entity.webhookPath, webhook_entity.method`,
and the stale copy answered the webhook with its old broken configuration —
which is why the webhook returned 200 while nothing happened. Each workflow
now carries a stable id, so a re-import updates in place.

**Git Bash rewrites POSIX paths.** `--input=/workflows` became
`C:/Program Files/Git/workflows` and the import silently found nothing.
Prefix docker commands with `MSYS_NO_PATHCONV=1`.

Duplicates to remove in the editor: `QfHHVtQllsF3eXww`, `SDqw85dQcCXP32qN`,
`v4ZQmvT9rvddCsSG`, `vaXjZDgf0nEYV5mB`, `cFWaBNmMTEPA2kiB`. Keep the three
whose ids begin `invoice`.

## What the workflows do

**Process a submission** (webhook). Receives `{"submission_id": "..."}`, calls
`POST /submissions/{id}/process`, and routes on the result: review needed, no
action, or a failure that outlasted the retries. The HTTP node retries three
times with a five-second wait and continues on its error output, so a failure
is visible rather than silent.

It deliberately does **not** check first whether the submission was already
processed. The API refuses to process a settled submission and reports what
was recorded, so re-implementing that check here would create a second opinion
about the same question — and the orchestrator would be the one that is wrong
after a race.

**Recover stalled work** (every fifteen minutes). Calls `POST /jobs/recover`
and separates "something still needs a person" from "nothing outstanding".

**Read pending notifications** (every five minutes). Reads
`GET /notifications?status=pending` and stops there. Nothing in this project
delivers a notification, and a workflow that marked them sent without sending
them would put a falsehood in the database. When a mail or chat node is added,
the next step becomes `POST /notifications/{id}/sent` naming that channel.

## Regenerating and importing

```powershell
.\.venv\Scripts\python.exe workflows\n8n\build_workflows.py
```

```bash
MSYS_NO_PATHCONV=1 docker compose exec n8n n8n import:workflow --separate --input=/workflows
```

The exports carry no secret. The credential is seeded separately, inside the
container, from the environment compose already gives it:

```bash
MSYS_NO_PATHCONV=1 docker compose exec n8n sh -lc 'umask 077; printf "%s" "[{\"id\":\"invoiceApiKey\",\"name\":\"Invoice API key\",\"type\":\"httpHeaderAuth\",\"data\":{\"name\":\"X-API-Key\",\"value\":\"${INVOICE_API_KEY}\"}}]" > /tmp/cred.json; n8n import:credentials --input=/tmp/cred.json; rm -f /tmp/cred.json'
```
